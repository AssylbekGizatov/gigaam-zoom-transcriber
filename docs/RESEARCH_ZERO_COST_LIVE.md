# Живая локальная расшифровка без платного потока: исследование

Дата проверки: **4 ноября 2026 года**. Это исследование источников и инженерных
вариантов, а не отчёт о проверенной реальной Zoom-встрече. Фактический статус
реализации и измерения нужно читать в README и отчёте тестирования проекта.
Цель: собственное приложение, GigaAM на компьютере, без Zoom Record, без
облачного STT, без RTMS-списаний и без сохранения аудио/видео встречи.

## Вывод для выбора архитектуры

Подход «приложение слушает звук на компьютере во время звонка» используется
существующими продуктами. Для него не требуется превращать наш код в облачный
сервис Zoom. Он технически отделяет две задачи:

1. **Звук:** получить вывод Zoom и, отдельно, местный микрофон; передавать короткие
   PCM-буферы непосредственно в локальный распознаватель.
2. **Кто говорит:** получить имя и признак активности из интерфейса встречи либо
   иметь отдельный официальный аудиоканал с ID. Смешанный звук сам по себе не
   содержит имени пользователя или Zoom ID.

Практический кандидат для Windows — WASAPI loopback + микрофон + необязательное
чтение активного спикера через Accessibility/UI Automation. Идею чтения имени
подтверждает не предположение о внутренностях конкурента, а документация Granola,
описанная ниже. Свой адаптер всё равно необходимо проверять на установленной
версии Zoom: общий интерфейс доступности не гарантирует конкретную структуру его
элементов. **Нельзя называть такую атрибуцию эквивалентом отдельного аудиопотока
с достоверным Zoom user ID.**

«Без сохранения записи» в этой архитектуре означает отсутствие WAV/MP3/MP4
на диске. Короткие аудиобуферы в RAM необходимы для распознавания. После
обработки они освобождаются; остаются текст и технические метаданные. Начать
распознавание только после завершения звонка без сохранённого аудио невозможно:
текст нужно строить параллельно звонку, а в конце завершить очередь и экспорт.

## SHAI.PRO и shainote: что удалось установить

[SHAI.PRO](https://shai.pro/ru) представляет корпоративную платформу и VoiceNote
Agent. Ссылка `voicenote.shai.pro` перенаправляет на
[shainote](https://shainote.ai/). На проверенных публичных страницах не найдены
скачиваемые ASR-веса, model card, лицензия на повторное использование модели,
описание её архитектуры или требования CPU/RAM/GPU. Поэтому нельзя утверждать,
что «SHAI Pro» — доступная нам бесплатная локальная модель, что она основана на
Whisper/GigaAM или что её внутренний алгоритм можно воспроизвести по маркетингу.

shainote описывает вход по ссылке **третьим участником** с записью встречи,
поддержку загрузки файлов, разделение спикеров и таймкоды. Заявлены казахский,
русский, английский и смешанная речь; «до 97%» — утверждение производителя,
не результат нашего теста. Free ограничен 3 часами в месяц с хранением записей
30 дней; локальное развёртывание относится к Enterprise. Это не удовлетворяет
нашему сочетанию неограниченного локального использования и отсутствия записи.
Источник: [официальное описание, механизм и тарифы shainote](https://shainote.ai/).

Полезная продуктовая идея: одна кнопка начала, состояние обработки и реплики
с именами и временем. Покупать сервис, создавать аккаунт или принимать его
условия для этого исследования не требуется и не выполнялось.

Recall публикует PAYG **$0.50 за час** как для бота, так и для Desktop SDK;
первые пять часов — пробный объём, а не бессрочная бесплатность. Отдельно
тарифицируются его встроенная транскрибация и длительное хранение.
[Официальная цена](https://www.recall.ai/pricing). В проекте такой поток не
должен включаться как скрытый fallback.

У Granola механизм имён опубликован достаточно конкретно: Accessibility читает
имя участника и признак текущего спикера; эта часть не захватывает экран или
аудио. При общем микрофоне, одновременной речи или неясном активном спикере
атрибуция ограничена. Если метаданных нет, остаётся разделение Me/Them.
[Speaker Tags](https://docs.granola.ai/help-center/taking-notes/speaker-attribution).
Это более полезный технический референс, чем обещание «всегда узнаёт каждого».

## Бесплатные системные механизмы Windows

[WASAPI loopback](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)
читает звук устройства вывода. Он работает в shared mode и не требует
аппаратного Stereo Mix. Обычный loopback содержит смешанный вывод приложений:
уведомление или музыка на том же устройстве могут попасть в транскрипт.
Микрофон нужен отдельным источником: голос местного пользователя обычно не
воспроизводится Zoom обратно ему самому.

[Application loopback Microsoft](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)
может ограничить захват заданным процессом и его дочерними процессами. Пример
требует Windows build 20348 или новее. Это предпочтительное расширение, если
реальная структура процессов Zoom и доступные средства сборки проверены;
нельзя обещать его работу лишь по наличию Windows 11. Пример пишет WAV, но API
не требует, чтобы наше приложение сохраняло полученные PCM в файл.

[UI Automation](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-uiautomationoverview)
даёт свойства и события элементов интерфейса. Наш адаптер должен читать только
нужное окно встречи, ограничивать частоту и объём обхода, не нажимать кнопки и
не собирать содержимое других окон. UIA Runtime ID — идентификатор элемента
интерфейса, **не Zoom account ID**. Обновление клиента, язык интерфейса,
свёрнутое окно и изменение layout требуют отдельных проверок.

## Имена, диаризация и неизбежные ограничения

Следующие положения — инженерные выводы из доступных каналов данных.

| Ситуация | Корректное поведение своего приложения |
|---|---|
| Свой микрофон | Отдельный источник «Я»/заданное пользователем имя; не выдавать его за подтверждённый Zoom ID. |
| Один ясный активный спикер Zoom | Имя из наблюдаемых метаданных и отметка происхождения `zoom_ui`; сохранять снимок имени. |
| Два одинаковых имени | Не объединять по строке имени; использовать отдельные наблюдаемые идентификаторы, если они есть. При отсутствии — неоднозначность. |
| Переименование | Новое имя для новых реплик; история остаётся со старым снимком. |
| Выход/повторный вход | Новая эпоха источника; не предполагать, что это тот же человек по совпадению имени. |
| Общий микрофон переговорной | Указывать источник комнаты, а не выдумывать конкретного человека. |
| Одновременная речь | Смешанный/неопределённый источник; один индикатор Zoom не доказывает принадлежность всех слов. |
| Потеря UI-метаданных | Продолжать ASR с «Не определён», показывать статус; не переносить последнее имя бесконечно. |
| Перегрузка CPU | Явный gap и счётчик пропуска; нельзя одновременно обещать ограниченную память, отсутствие записи и бесконечный backlog. |

Диаризация отвечает на вопрос «похожи ли эти фрагменты на одного говорящего»,
а не «какое имя и Zoom ID у человека». Для неё есть локальные варианты:

- [pyannote Community-1](https://huggingface.co/pyannote/speaker-diarization-community-1):
  16 kHz mono, локальная обработка и offline use, CC-BY-4.0; скачивание требует
  принятия условий и передачи данных профиля Hugging Face. Эти условия не
  принимались. Наличие free weights не отменяет CPU/RAM-стоимость и ошибки.
- [SpeechBrain ECAPA-TDNN](https://huggingface.co/speechbrain/spkrec-ecapa-voxceleb):
  Apache-2.0, эмбеддинги/верификация голоса на 16 kHz; не готовый источник имён.
  Сходство эмбеддингов не равно подтверждённой личности.
- [diart](https://github.com/juanmc2005/diart): MIT streaming-диаризация.
  Лицензии и доступность используемых моделей проверяются отдельно от кода.

Для первого рабочего режима рационально использовать уже имеющийся GigaAM,
раздельный mic/loopback и наблюдаемые имена. Добавлять ещё одну нейросеть стоит
после измерения остаточного CPU-бюджета и ошибок атрибуции. Кластеризацию нужно
показывать как «Спикер N» с возможностью подтверждения имени, а не маскировать
под официальный Zoom источник.

## Требования к проверке выбранного решения

Этот раздел задаёт критерии, а не утверждает, что они уже пройдены.

1. **Настоящий вывод звука:** разрешённая тестовая речь проходит через устройство
   вывода Windows и читается loopback, а не подаётся прямо в ASR из файла.
2. **Настоящая Zoom-встреча:** два удалённых участника, местный микрофон,
   короткие реплики на kk/ru/en и смешанной речи; никакого Zoom Record.
3. **Имена:** смена активного спикера, одинаковые имена, rename, rejoin,
   перекрывающаяся речь, общий микрофон, потеря UI-метаданных. Отдельно измерить
   ошибки имени; WER текста их не покрывает.
4. **Время:** единые монотонные часы для аудио и событий UI; начало сеанса
   захвата явно отличается от начала встречи при позднем запуске.
5. **Ресурсы:** модель + Zoom + интерфейс одновременно; RAM peak, CPU, realtime
   factor, задержка до финального текста, длина очереди и пропуски. CPU-процент
   и RTF не заменяют друг друга.
6. **Приватность:** не создаются аудио/видеофайлы, runtime ASR не вызывает
   внешний STT, ошибки/логи не сохраняют содержимое буферов или секреты.
7. **Завершение:** Stop прекращает новые данные, обрабатывает принятые буферы,
   сохраняет текст и экспорт; авария не превращает неполный транскрипт в полный.

Под «без затрат» здесь понимаются отсутствие дополнительной подписки,
оплаты за минуты, облачного inference и арендуемого сервера. Используются уже
имеющиеся компьютер, соединение и Zoom-аккаунт; электричество и нагрузка ПК
физически остаются. Нельзя переводить этот режим на RTMS или сторонний API при
ошибке захвата незаметно для пользователя.
